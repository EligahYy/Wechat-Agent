# 半托管欧区备货用户助手：产品重建设计

评审基线：2026-11-08，已发布代码 v0.6.1（`ba267f5`）。本文是新一轮产品方案，不代表功能已上线。替代此前增量改造、客户收口和文档 Agent 草案。技术实现见 [系统与 Agent 架构](SYSTEM_ARCHITECTURE.md)，交付标准见 [验收与重建计划](ACCEPTANCE_PLAN.md)。

## 1. 产品到底帮助用户完成什么

用户是跨境电商平台的产品／运营，通过个人工作微信向商家介绍欧区半托管备货机会、头程物流价卡及活动，随后协调商家与头程服务商推进备货。私信和群聊很多，既需要推进当前需求，也需要记住尚未形成需求的沟通，适时激活历史客户。

业务重心是促进商家在平台备货：先理解经营市场、品类、平台合作意向、库存与补货计划，再判断物流成本等阻力。头程报价和三方协调是推进手段。客户档案不能退化成运输订单清单；拿到唛头、车牌或服务商报价也不能等同于平台备货转化。

核心结果是：**用户打开工作台，知道今天值得联系哪些商家、为什么、怎么在微信找到对方、应该说什么，并且处理结果能延续到下一次判断。**

完整业务链路：

> 微信持续接入 → 识别商家与沟通归属 → 维护每位客户的档案和备货批次 → 根据最新进展决定下一步 → 用户处理今天该联系谁 → 新回复与人工结果更新同一档案。

客户数、生成任务数、模型请求数都是运行指标，不是产品成效。首要指标是建议有用、对象正确、状态可信、人工负担下降；后续再观察备货转化，不能把转化归因于助手单一因素。

### 1.1 已确定的要求

| 历史诉求 | 本轮产品决定 |
| --- | --- |
| 个人微信必须保留，账号完全用于工作 | 首版运行在个人 Mac，通过 wx-cli 持续读取私信和普通群聊；不要求迁移企业微信 |
| 不依赖旧导出项目 | wx-cli 为主入口，文件导入只保留一个标准入口，不兼容旧项目专有格式 |
| 大模型自动建档、规划，人工只做关键确认 | 默认自动落下有依据的资料和进展；仅把影响当前行动的歧义交给人 |
| 按同一联系人分类 | 首版一位稳定微信联系人对应一份客户档案；跨私信／群聊收口，暂不做自动公司合并 |
| 按批次记录，不同问题都在本人档案下 | 初步沟通、资料、批次、行动、确认统一隶属客户；不按问题新建客户卡片 |
| 白名单内不做客户跟进 | 白名单在页面统一称“免跟进名单”；联系人排除与整会话排除明确区分 |
| 近15天先产生价值，历史后台补齐 | 最近15天优先整理，可用客户逐步出现；历史完成度单独显示，不等全库跑完 |
| 昵称、群名可回微信查找 | 名称从源端获取；客户卡必须有真实定位依据，不让模型命名补空 |
| 海报、图片、价卡很重要 | 附件属于业务来源，纳入接入与识别设计；未读图片不能当作“无需求” |
| 旧待办不重要，推倒重来 | 保留消息、名称、排除决定、凭据配置和用量；旧 AI 结果只读留存，不用于新推理 |
| 极简、参考 PersonalAI 方向 | 一个业务 Agent、有限工具、持久客户记忆、可回放执行；不引入多 Agent 协作框架 |

这里借鉴的是“少组件、可读记忆、有限工具”的设计原则，并未把某个未指明的 PersonalAI 项目当作已核验技术依赖。

### 1.2 第一版完整业务闭环的边界

包含：初步沟通沉淀、当前批次推进、明确约定回访、客户级确认、身份定位、免跟进管理、接入与分析可观测性、人工处理结果学习。新价卡驱动的历史客户激活需要有效素材信息，单列为随后一个交付里程碑，但底座现在预留。

发送微信、加好友、建群均由用户操作。首版不做企业组织树、多账号归并、销售绩效、复杂审批或自主执行微信操作。

## 2. 现有实现为什么没有达到预期

本次核对的是仓库代码及用户反馈，没有访问用户 Mac 上的真实客户库。以下区分代码事实与仍需源端实测的问题。

| 现状及证据 | 对业务的影响 | 重建决定 |
| --- | --- | --- |
| [planning.py](../src/wechat_agent/planning.py) 以会话内约16条／3500字符分片；[analysis.py](../src/wechat_agent/analysis.py) 拼有限事实和后续6条消息 | 网络分片成了理解业务的边界，跨私信／群的后续答复容易不足 | 分片只作传输单位；业务理解以客户、相关事件及后续结果为单位 |
| [crm.py](../src/wechat_agent/crm.py) 的计划以客户＋名称唯一；行动使用模型 action_key 和文本相似度补偿 | 同一批改个名字可重复，近似文字也可能对应不同义务 | 本地稳定批次、事件、行动标识；模型只能选择或提出新对象 |
| crm_reviews 按账号＋问题文字＋证据唯一，确认后记录自由文本再调度 | 换说法／多一条证据就可能重复；确认难以精确约束以后分析 | 客户内结构化决策，按争议对象与字段归并，持久保存决定 |
| [web.py](../src/wechat_agent/web.py) 客户列表直接查询 crm_customers，缺少统一人物排除条件 | 任务过滤与客户列表可见性不一致 | 所有业务查询共用资格规则，名单变更立即影响全站 |
| 客户详情主要查询本人群发言和私信 | 群内服务商回答、我方解释可能不在客户业务脉络中 | 保存相关事件的完整来源片段，多方回复关联到同一客户／批次 |
| 缺少约定日期时按阶段补2／3／7个工作日 | “有一段讨论”容易变成“应该去催” | 必须有行动理由；约定、建议、条件触发分开，沉默不自动到期 |
| 会话模型分类存成全会话类型，部分证据过滤沿用它 | 混合群的短期片段可能影响整群资格 | 模型按片段判断相关性；只有用户明确排除能形成持久硬规则 |
| 有名称同步、响应缓存、版本与预算防护，但不构成业务效果评测 | 接口成功、JSON合格仍可能找错人、误开待办 | 先建立真实场景金标准与回放，再用真实 DeepSeek 验收 |
| [identity.py](../src/wechat_agent/identity.py) 能读取部分联系人信息，媒体未自动理解 | 无法仅凭仓库确定所有群成员名、图片内容均完整 | 先建立源端能力及缺失报告；不把姓名或媒体缺失归咎于模型 |

已经有用的资产继续利用：只读采集、消息修订、断点、身份同步、模型网络配置、预算台账、鉴权和原文证据。业务状态与页面组织重建，不要求重装微信或重新提取已有有效密钥。

## 3. 业务对象与状态：少对象，关系明确

### 3.1 首版只让用户理解三个对象

1. **客户**：一个已识别为商家的真实微信联系人。包括初步沟通、资料、顾虑、近期变化、所有批次、下一步、待确认。
2. **备货批次**：该客户一次具体备货意向及其进展。可以跨多个群；一个群可以谈多批。
3. **下一步**：当前值得我做的行动，或者等待、条件触发。属于客户，可再属于某批次。

来源消息、联系人索引、模型执行记录是后台数据，用户不需要先填写它们才能使用。资料未知允许为空。

首版按工作账号＋真实联系人ID唯一建档。备注变更不会重建，同名联系人不会合并。一个人代表多个店铺时，在档案与批次记录店铺属性；不同联系人同属一家公司暂时各自建档并可关联说明，不自动合并。后续确有使用需求再增加经过确认的组织关系。

### 3.2 初步沟通与批次进展

```mermaid
flowchart LR
    A[初步沟通：客户级记录] -->|出现具体备货意向| B[需求确认]
    B --> C[报价沟通]
    C --> D[商家决策]
    D --> E[备货中]
    E --> F[已报告发货]
    F --> G[已结束]
```

“初步沟通”替代“接洽培育”。它是客户级沟通内容，不强制产生一个空批次。批次从“需求确认”开始，不要求价格、货量、日期全部齐全。

| 内容 | 应记录 | 何时产生行动 |
| --- | --- | --- |
| 我方发送海报／价卡 | 触达记录、素材引用和版本、适用线路 | 仅发送不产生回访任务，也不证明对方看过或有兴趣 |
| “了解一下”“英国费用太高” | 兴趣、顾虑及原话 | 有明确问题需我回应时才行动 |
| “暂时没货，月底再说” | 暂无计划、约定原文、时间解释 | 可形成客户级回访；历史回填不能让多年约定集中逾期 |
| “下周有三方英国货，怎么走？” | 建立具体批次，记录已知参数和缺失信息 | 必要的需求确认或报价推进 |
| “预计明天发”“下午出唛头” | 发货计划／准备动作 | 不标记已发货 |
| “这一批今天已经发出了” | 在对应批次记“已报告发货” | 关闭该批已失效的备货催办；不结束整位客户 |

阶段允许证据充分时跳转；真实变更可回到报价沟通，但必须记录原因和发生时间。不是单调递增的销售漏斗。已结束／取消的同批不能被旧消息重新打开；后续新需求建立新批。

“暂停”是批次推进开关，保留当前阶段；“取消”是结束结果，保留原因。“已报告发货”表示聊天中的报告，尚不等于平台系统核验发货。首版不接物流履约系统。

客户本身没有“已发货＝结束客户”的状态：可以同时保留已结束旧批、推进新批、进行下一轮初步沟通。

### 3.3 三种开关不能混用

| 状态 | 客户列表 | 新消息整理 | 自动联系建议 |
| --- | --- | --- | --- |
| 正常客户 | 显示 | 正常 | 依证据与节奏决定 |
| 暂停联系客户 | 显示，可筛选 | 继续维护资料和进展 | 暂停，直到用户恢复或约定暂停期结束 |
| 人物免跟进 | 不作为客户显示，客户搜索／计数／今日也排除 | 本人私信仅归档；正常商家群中的发言可作为他人的业务背景 | 不以此人为自动外联目标 |
| 会话免跟进 | 不因该会话建立客户；不影响此人在其他正常会话的资格 | 整会话只归档，不供模型检索 | 该会话不产生建议 |
| 某一批已结束 | 客户仍显示 | 继续 | 该批不再催备货；其他批和未来有依据的回访正常 |

白名单不是“忽略所有包含这个人的群”，也不是“所有群成员都是非客户”。模型认为某段是内部协作可不产生业务结果，但不能悄悄修改用户的免跟进规则。

### 3.4 所有数据有去处

原始消息只保存一份。业务资料可引用到一个或多个客户／批次；多人共用的价卡保留共享来源，不复制成多条独立消息。

没有客户归属的内部协作、已排除聊天、无效消息、未识别媒体进入数据档案及覆盖报告。归属不明的业务片段先保留后台待归属，不强行创建“未知客户”。只有已经定位到具体联系人且歧义会影响当前行动时，才在该联系人卡片下提出关键确认；确认商家身份前不计入正常客户。

## 4. Agent 应该为用户做的事

| 能力 | 输入与判断 | 业务输出 |
| --- | --- | --- |
| 识别人和关系 | 真实来源身份、私信对端、群上下文、已确认角色 | 知道谁是商家、谁在协助，不自造名字 |
| 整理初步沟通 | 发过的材料、商家反馈、兴趣及顾虑 | 持续维护客户近况，资料不足也可建有效档案 |
| 归并备货批次 | 已有批次、引用关系、目的地、货量、窗口、新旧批证据 | 更新已有批或建立新批；不靠群名和标题匹配 |
| 判断进展 | 请求及随后答复、取消、改期、报告发货 | 同一事项保持最新状态，不从历史提问重复造任务 |
| 安排下一步 | 谁负责、是否仍未解决、是否需要我行动、联系是否合适 | 给出行动／等待／无需行动，说明理由及依据 |
| 准备联系 | 真实联系入口、当前诉求、已确认素材、有效报价 | 有上下文的话术草稿，不编价格和承诺 |
| 消化人工反馈 | 完成、改期、暂停、身份／批次纠正 | 更新同一档案，后续分析继续遵守 |
| 激活历史客户 | 历史兴趣＋现在有效的触发条件 | 匹配有理由的建议，避免无差别“很久没联系” |

### 4.1 今日行动的进入条件

必须同时满足：目标商家有效且未排除；人能定位；有当前未解决的事项或已到约定回访时间；确实需要我行动；来源与最新后续检查有效；客户未暂停；对应批次未终止；没有同一义务的有效重复行动。

三类时间明确展示：**约定时间**来自原文；**建议时间**来自可解释策略；**触发后再联系**等待事件，不伪造到期日。没有明确日期，也没有必要跟进理由时不补一个日期。

等待服务商或客户回复不等于每天提醒用户。先保留等待状态；达到明确约定或可配置的合理复查时机才重新判断。复查作业到期也不直接等于业务行动到期。

### 4.2 用户只确认有后果的选择

确认聚合在客户档案和客户卡片内。例如“这位是商家还是服务商”“这次发货指第一批还是第二批”。显示一个判断、候选选择、简短理由，证据默认折叠。允许“暂不判断”。

同一客户的多个不同问题可以并存，但只有一个客户卡片；同一争议追加证据，不增加卡片。相同证据支持两个不同事实本身不是重复错误。判断是否重复，要看争议对象／字段／业务义务，而非原文是否出现两次。

用户明确的角色、排除、批次归属、暂停决定成为持久约束。后续新证据若冲突，先保留历史与冲突，不能被模型默默覆盖。

批量“暂不处理”只暂缓提示，不把未知答案变成已确认事实。移出免跟进名单后按当前证据重新评估，不能直接恢复多年以前的旧催办。

### 4.3 历史激活怎么避免变成机械催促

有效触发：匹配其线路的新价卡／政策、曾约定的月份、已明确的周期备货窗口。沉默时长只作排序信号，不能独立创建任务。

每条建议说明“此前对什么感兴趣、这次有什么变化、为什么适合现在联系”。素材必须有适用范围和有效期；过期或未核实素材不能支持报价承诺。无回复时设置冷却期，有明确拒绝／暂停则遵守。冷却长度和每天建议数量在试点后调整，不作为写死业务常识。

## 5. 页面围绕使用动作组织

一级导航收敛为 **今日、客户、数据、设置**。待确认是客户维度的筛选；批次在档案内；分析进度由全局状态条和数据页进入。

### 5.1 今日

默认按客户聚合，一位客户一张卡；显示真实备注／昵称、建议联系理由、当前批次、最重要下一步和时间。其他独立行动折叠为“另有2项”，不在数据库硬合并。

页签：`该联系`、`待确认`、`等待中`。分别按客户计数，明确“3位客户／5件事项”。建议优先级按明确到期、阻塞备货、近期有效回访，再到激活建议排序；模型形容词不决定排序。

卡片操作：查看客户、复制联系线索、准备话术、记录处理。复制话术不记录已联系；读取到实际发出的微信可更新最近联系时间，但仍不能据此推断事项完成。

虚构卡片示例：

> 张先生 · 微信备注“英国小家电张先生”
>
> 英国普货｜11月第一批 · 商家决策
>
> 今天联系：确认是否接受补充后的附加费方案。昨天服务商已答复，商家尚未表态。
>
> 约定今天14:00前反馈 · 来源：私信及“英国备货对接”群
>
> 查看依据 / 准备话术 / 记录结果

初步沟通示例则为：“月底按约定问一下英国备货安排”，批次栏留空，不为了布局补建批次。

### 5.2 客户档案

顶部固定真实定位信息：备注、昵称、可用微信号、相关群名及原文时间锚点。群成员名是群内属性，不能当作全局唯一身份。源端无名称时显示“姓名待同步”与来源群，不让模型猜名；定位质量不足的客户不进入可直接联系列表。

内容顺序：当前近况和下一步 → 需要确认 → 初步沟通／长期资料 → 当前批次 → 历史批次 → 沟通重点。摘要逐项可点证据；长期偏好与某批货量分开。

默认展示需求、报价、顾虑、约定、阶段变化等重点事件，原文在展开后按时间显示上下文。寒暄可以折叠，不能删除原始消息或全局剔除有语义作用的“收到／好的”。报价材料、图片及未识别状态要可见。

列表每页50位客户，搜索真实备注、昵称、可用别名、已确认店铺属性；保留筛选与滚动位置。免跟进人物不通过“全部客户”选项绕回客户列表。

### 5.3 数据

- 接入状态：微信源服务、本地后台、最后成功同步、名称与媒体缺失。
- 分析状态：近15天进度、历史覆盖、当前整理客户／会话、失败原因、实际用量与待核实用量。
- 分析范围：`正常处理`／`免跟进`页签；会话／人物切换，每页50条。每个页签只出现对应增删操作，跨页不暗中保留勾选。
- 原始档案：查看全部本机可见记录、待归属、不可读媒体、隔离行。一个文件导入按钮在这里。

大屏应回答“卡在哪里、已有多少可信结果、缺哪些资料”，而不是只展示越来越大的消息数。进度分母以源端可见、允许分析的数据计算，并明确缺口。

### 5.4 设置与交互细节

设置保留账号、DeepSeek、预算、联系偏好、备份恢复。技术日志和令牌进入诊断折叠区。常规使用无需反复调整队列或处理大量错误分片。

采用清晰的字体层级、紧凑标签、克制留白。列表操作后原地更新，保留选择焦点；名单调整提供撤销。加载、空结果、未开启分析、分析失败、资料不足分别呈现，不能统一写“暂无待办”。

过渡以轻微位移和透明度为主，建议160–220毫秒，并支持减少动态效果；键盘可操作、侧栏关闭返回原位置、窄屏不溢出。先把信息和操作做对，再调整动画，不以模仿官网动效代替可用性。

## 6. 一条完整业务如何贯穿系统

以下均为虚构场景：

1. 私信中给张先生发德国价卡。他是已确认商家：记录一次初步沟通；无具体货、无回复约定，不生成批次或任务。
2. 张先生问英国费用。记录英国兴趣；通用问价仍可在客户级处理。
3. 张先生说“下周有三方英国货”。建立批次B1；需求不全也可进入需求确认。
4. 拉群与服务商报价，群中服务商回复附加费。整段关联张先生的B1；服务商不被新建为客户，已回答的问题退出下一步。
5. 商家约定周五决定。B1进入商家决策，产生一个客户卡片；其余问题都收在张先生档案内。
6. 商家说“这批已发”。B1为已报告发货，停止该批备货催促。历史询价回填不会重开。
7. 两周后问另一批货。建立B2，保留B1历史。客户仍为张先生，群没有产生第二位“客户”。
8. 后来有更适配英国线路的新价卡。若材料有效且无暂停／拒绝约束，产生有理由的激活建议；不会因为B1结束就永远不再联系。

## 7. 本轮设计决议与开发顺序

产品方向确定为客户记忆和今日行动；一个业务 Agent 管理解读，确定性程序管理身份、规则、版本与写入。Agent 不承诺绝对准确，准确性通过证据、上下文、评测和有限人工纠正建立。

先做来源及身份验收、业务金标准；再打通一个客户跨私信／群聊的完整周期；之后实现最近15天和全量历史重建；最后增加价卡驱动激活及视觉细化。每阶段有可演示产物和业务验收门槛，详见 [验收计划](ACCEPTANCE_PLAN.md)。

已开始按本方案实施M0，当前交付范围见 [实施状态](IMPLEMENTATION_STATUS.md)，交互细节见 [视觉与交互规范](UI_DESIGN.md)。旧实现保持可运行，新客户引擎尚未切换；此前未发布草稿不作为实现前提。
