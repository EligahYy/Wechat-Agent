# 产品方案：半托管欧区备货用户助手

更新：2026-11-15（北京时间）。实施基线，仅依据仓库清空后重新讨论的方案及最新交互修订。

## 1. 产品目标

把工作微信中从首次接触到现在的聊天，整理为按联系人归一、持续更新、可核对来源的商家档案。

主链路：**接入私信与群聊 → 统一联系人 → 确认身份 → 整理商家全部相关资料 → 形成档案与独立备货记录 → 按日及按需更新**。

用户无需手动建立商家、项目或逐条批准线索。人工操作集中于身份、业务范围设置、资料纠正和必要补充。

有价值的数据必须归属明确、保留时间和语境、结论具体、可查来源、错误可纠正。没有读懂的内容保留为具体缺口，不能包装成空泛总结。

## 3. 联系人和整理范围

### 3.1 唯一身份

- 主键为工作账号 ID + 来源稳定联系人 ID；同人在私信、不同群与不同昵称下归为一人。
- 搜索只匹配当前可用微信昵称／备注，以及页面实际采用的补充姓名；不匹配wxid、来源群名或未展示的历史别名。同名不同人不合并，改昵称不新增客户。
- 群聊是消息来源，不是客户。一个群可以关联多位联系人，消息原文只归档一次。
- 工作账号本人为“我方”，不建立商家档案；发言作为上下文保留。
- 姓名优先使用真实源端备注／昵称，不让模型推测人名、群名或英文公司别名。
- “复制微信名称”只复制当前可确认的全局备注／昵称。缺少全局名称时，群名片可补位并标注“群内名称”；它不保证是真实姓名或最新昵称，不能作为全局微信名称复制。

### 3.2 身份标签

| 身份   | 展示颜色 | 整理规则                                           |
| ------ | -------- | -------------------------------------------------- |
| 商家   | 蓝       | 自动生成并更新客户档案                             |
| 服务商 | 紫       | 归档，相关回复可支撑商家事实，不作为客户分析目标   |
| 平台   | 绿       | 归档，相关平台信息保留为上下文，不作为客户分析目标 |
| 待识别 | 琥珀     | 尚未确认身份，暂不进入商家整理                     |

“我方”是参与人显示类型，使用紫色加粗，不是第四种业务身份。

人工身份设置优先，支持单个与批量操作。首版以人工批量确认身份为实施默认，不新增自动扩张分析范围的分类 Agent。模型身份建议可在资料链路验收后另行设计。

身份改变不会删除原文。改为非商家时退出商家列表，撤销其尚未开始的分析；已执行请求的结果不得继续发布为该商家的新档案。改回商家时重新按来源版本判断是否需要整理。

### 3.3 业务活跃范围与全量管理

工作台保留商家档案与业务活跃联系人。全量归档不删除，在设置的联系人管理中搜索、单个或批量加入／移出业务范围。身份与业务范围独立，人工移出最高优先，只有人工重新加入才能恢复。

自动范围包含已确认身份、近90天真实私聊／结构化直接互动，以及近90天本人在群内明确表达的询价、备货或发货需求。其他人的群发言不算本人活动；同名不同ID不合并。模型／来源覆盖不完整时，近期实际群发言者作为临时候选保留，显示“群需求识别待完成”；模型已给出负面结论也必须有完整、未变化的覆盖证据才能移除临时候选。分类不自动改变身份；只有范围内已确认商家可以进入档案分析。

## 4. 微信资料接入

### 4.1 归档原则

原文、附件文件、附件解析结果分别保存。消息保留来源 ID、会话、实际发送人、时间、引用关系、版本及原始类型。

- 私信：保留双方完整往来。
- 群聊：完整归档，按说话人、回复、提及、订单与连续上下文关联目标客户。
- 不能只读取客户自己发的话；服务商“已发出”的回复同样可能是关键证据。
- 无法确定归属的群内容仍保留，但不能变成某位商家的确定事实。
- 不在模型阅读前按“价值”大量删减消息，不因问候、短回复或系统消息简单丢失连续语境。

联系人、备注与群名在采集阶段读取，不依赖模型生成。名称缺失时保留可定位的 ID、来源、时间和具体原因，提供重试；不展示一长串没有出处的“待同步群名”。

### 4.2 图片和文件

接入目标包含本机可获得的图片原件／缩略图与普通文件。是否能获取，取决于用户 Mac 上源端可见数据与文件是否存在，实施阶段用真实样本验收。

附件分别显示：未获取、本机缺失、获取失败、原件／缩略图、待解析、解析失败、已解析。取得文件不等于读懂内容。

首版验证图片文字与价卡、PDF、CSV／Excel 的报价及装箱资料；其他格式先保留文件并标明未解析，不声称全格式支持。模型若不能直接识图，使用独立 OCR／解析器，再把解析内容与原图位置交给模型。

源端只保证当前可见历史，不承诺找回隐藏、已删除或从未同步的消息。缺少附件不能把明确的文本发货事实变成“未知”。

### 4.3 手动导入

设置内保留一个导入入口。CSV／JSON 的最少信息为来源批次、会话标识、发送人标识、时间、消息标识及正文；附件可选。允许列映射与导入预览，归属不足的行报告具体问题。

去重按来源消息身份完成，不把文本相同的两次对话合并。重复导入不增加记录；导入不能凭昵称合并联系人或覆盖已有原文。

## 5. 客户档案模板

固定字段保持精简。每条模型结论应关联支持该结论的消息或附件位置；人工纠正和补充标明人工来源。字段可以未提及、待核实，不强行填满；没有完成相关资料处理时，不能用“未提及”掩盖未读或解析失败。

| 部分     | 字段                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 联系人   | 来源备注／昵称、稳定 ID、人工身份、来源会话                                                                  |
| 货品情况 | 主营类目、具体货品、特殊属性、货量                                                                           |
| 物流需求 | 常见起运地、目的国家／地区、仓库及邮编、运输方式诉求、清关／税务、时效、价格关注、提货及末端服务、顾虑与痛点 |
| 沟通情况 | 当前具体摘要、沟通状态标签、最近业务沟通时间                                                                 |
| 备货记录 | 每批时间、货品与货量、路线／运输要求、关联单号、当前进度、来源                                               |

货量、价格与服务要求保留单位、适用批次和时间，不把一次报价自动概括为永久偏好。

用户可以修改固定字段；尚无固定字段承载的信息写入“补充资料”。补充资料按客户及货品／物流分组保存，标记人工内容，可修改或删除，不生成虚构的聊天来源。不引入任意自定义字段配置系统。

人工纠正与模型记录分开保存。后续分析能看到人工约束，不能静默覆盖；若新消息与人工内容冲突，保留新来源并指出具体差异。

## 6. 沟通标签与备货进度

### 6.1 客户当前沟通

可多选：**初步沟通、需求沟通中、询价中、方案对接中、备货中、暂缓、暂无新需求记录**。

标签归纳当前仍有效的事项，不是整位客户不可逆的销售漏斗。资料不足时列出缺口，不默认填“初步沟通”或“暂无新需求记录”。

不同活跃事项可以产生多个标签；“暂无新需求记录”与需求沟通中、询价中、方案对接中、备货中等活跃标签互斥。“暂缓”针对具体需求，不能把同一客户其他仍进行的需求一并暂停；有活跃需求时以其沟通标签为主，批次内保留暂缓进展。跨标签冲突需回看对应事项，不能仅按最新一句话覆盖。

### 6.2 批次单独记录

每个新需求／备货批次独立保存，支持沟通、询价、方案对接、备货、已走货、已结束、暂缓等进展。已走货与已结束属于批次，不是整个客户的终态。

- 旧批已走货、新批询价：客户显示“询价中”，两条备货记录分别保存。
- 已走货后查询单号、轨迹、卸货、车牌或签收：优先更新原批次，不制造新发货需求。
- 明确“新一批”或上下文能证明独立的一次需求时建立新记录。货品、货量、目的地或周期变化也可能只是原批修改，不能单凭字段变化自动新建；无法确定是否独立时保留疑点和来源。
- 单号不是已发货的充分条件。已有单号且沟通实际发出、发车、出境、卸货等履约信息时，应识别已走货。
- 系统登记滞后不否定原文“已经发出”；预计到达不能当成已到达。

单号支持手工补充多个订单号、运单号、柜号，去重保存；手动录入单号不自动修改批次进度。

## 7. 同步、整理与资料状态

同步是把微信新记录归档；整理是让模型更新商家资料。不能只检查本地缓存就提示“微信没有新消息”。

| 资料状态 | 含义                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 待整理   | 已有可用资料，但尚未形成首份客户档案                                         |
| 待更新   | 已有可用档案，有尚未处理的新增／修订、解析或人工约束变化；或显式重算尚未完成 |
| 已更新   | 当前已获取资料版本已被成功整理；不代表源端历史绝对完整                       |
| 暂无资料 | 尚无可整理的来源，提供同步入口，不当作“无需求”                               |

来源同步是否成功、任务是否运行，与上述资料状态分开记录。失败、缺口和重试就近显示，不新开一套待确认任务系统。

资料状态之外保留“整理完整性”：分段失败、尚有待处理附件时可保留已有依据的局部档案，但显示整理不完整，并保持待更新；无首份可用档案则待整理。源端本就缺失的文件或不支持解析的格式记录为明确缺口，不假装仍在后台处理，也不因此无限重试。“已更新”不表示已读懂未知格式或找回缺失历史。

## 8. 更新与操作规则

- 目标每日一次，按 `Asia/Shanghai` 计算；默认08:30。当前只保存偏好，自动执行由M4接入。
- 首次按客户整理全部相关可见历史；之后仅处理资料版本变化的商家，不每收到一句话调用模型。
- 第一版增量以准确性优先：新消息触发后重新阅读该客户相关历史；长历史分段复用时必须证明覆盖与来源正确。
- 上下文按输入快照持久化，不依赖模型会话记忆；分段执行覆盖和事实正确率分别验证。详细实现见 [模型执行方案](MODEL_EXECUTION.md)。
- 工作台“同步并整理”：刷新联系人／会话资料并拉取最新消息 → 模型整理待处理商家 → 校验并更新客户资料。
- 客户页“同步并整理此客户”：相同链路，仅读取该客户私信及相关群聊，只整理并更新这个客户，不顺便分析其他群成员。
- 不单列主页“刷新联系人”：普通同步已包含元数据刷新。独立元数据刷新接口保留用于诊断，不代表刷新了聊天消息。
- 当前尚未完成档案发布闭环；整理能力未接入时明确显示“原文已同步，档案整理尚未接入”，不宣称客户资料已更新。
- 非商家可以同步原文，不运行客户分析。
- 只有同步成功且无新增时才能提示“没有新消息”；没有模型输入变化则不重复调用模型。
- 停止本次：不再发起后续请求，保留已归档消息与已完成结果，当前请求结果不得被误发布。
- 继续本次：从真实未完成工作恢复；空闲或已完成时不出现暂停／继续。
- 程序关闭或睡眠错过计划后，重新运行时补检查一次，不重放每天的重复任务。
- 应用未运行时首版不承诺自动唤醒；关闭每日计划只停止新计划，正在运行的操作仍用“停止本次”控制。

切换模型、档案模板或整理策略不立即对全部联系人重跑。先以真实样本回放验证，再在设置的维护入口选范围重新整理；原文与人工资料保留，重算失败不替换旧档案。常规同步发现无新增但存在未完成整理时，提示“没有新消息，仍有待整理资料”，不能等同于无需分析。

模型和 OCR 用量保留记录，不设置日预算硬上限。网络重试必须有边界，失败显示原因与重试入口，不靠不断消耗请求掩盖错误。

## 9. 当前状态与验收基线

当前实现与Mac验收统一见[实施状态](STATUS.md)：M1及M2任务1—3完成云端开发；M2任务4—7、M3—M5按计划实施。模型档案发布、人工资料、媒体解析与日调度未形成真实闭环。方案中的目标行为不能当作已实现能力。

以下必须使用真实接入或脱敏回放验收，不能由 UI 演示或合法 JSON 代替：

1. 同人跨私信／群只生成一个档案，同名不同人不串资料。
2. 群内服务商回复能正确支持对应商家的事实；不能把整群数据算给一个人。
3. “已发出但系统尚未登记”“已发车／已出境”等明确样例识别为已走货。
4. 旧批发货与新批需求并存；历史履约沟通不生成新需求。
5. “卡航可以，然后海运呢”保留两种诉求，不误写成汽运。
6. 重要结论可查原文；数字、单位、时间及附件位置可核对；未知和遗漏明确记录。
7. 重复同步幂等；同一任务不会并发重跑；失败／停止不产生空档案覆盖旧资料。
8. 用户纠正与补充可长期保存，更新后不丢失。

抽取约 10 位有代表性的真实商家作为首轮样本，另留一组复测。同时报告正确、错误、漏提和资料不足，不能通过删除错误内容提高表面正确率。关键回归样例零错误、展示引用全部可定位，再扩大自动批量运行范围。

## 10. 消息查阅

客户详情保留沟通原文入口，默认进入最新全部来源双栏。消息来源须有本人真实发言或可验证私聊，不能仅凭群成员目录。日历蓝点表示本人发言、灰点表示会话上下文，按北京时间选日，右侧保留当天所有人物上下文；本人按稳定ID高亮和前后定位。回到最新读取已同步归档，不暗中发起来源或模型调用。转发、媒体等技术载荷只做展示摘要，底层证据不改写。默认入口及布局以[交互方案](INTERACTION_DESIGN.md)为准，不能恢复被替代的全历史分页按钮或旧次级入口安排。
