# 基础产品方案：先建立有价值的客户资料

更新：2026-11-10。状态：产品设计与验证方案，新应用尚未实现。

## 1. 本阶段的目标与边界

用户通过个人工作微信与商家沟通欧区半托管备货，并协调服务商。产品先帮助用户准确理解一个客户从首次接触到现在的情况。

本阶段只交付三项能力：

1. 读取、归档并浏览微信资料，覆盖文本、引用消息、可获取的图片与文件。
2. 统一私信和群聊中的联系人，按联系人批量管理参与整理的范围。
3. 自动整理客户资料、沟通历史和当前业务情况，并可核对来源、纠正错误。

待办生成、提醒、跟进建议和处理规则放到后续阶段。本阶段的数据模型不预先围绕待办种类或跟进状态构建，也不要求用户逐条确认模型线索来换取完整档案。

“有价值数据”需要同时满足：归属明确、保留时间与语境、结论具体、可查来源、错误可纠正。资料不足时说明具体缺口，不能用一篇空泛总结掩盖缺失。

## 2. 联系人、群聊与资料的关系

### 2.1 一个人只有一个身份

联系人按“当前工作账号＋来源稳定联系人ID”归一。微信备注、昵称、群昵称和曾用名都是显示信息，不作为合并依据。

| 场景 | 处理 |
| --- | --- |
| 同一人在私信和多个群出现 | 同一联系人、同一档案；资料保留各自来源 |
| 联系人改备注或群昵称 | 更新显示与别名，不建立新联系人 |
| 两个人昵称相同 | 保持独立，可查看微信ID及来源会话辨别 |
| 一个群有多位商家和服务商 | 按实际说话人及事项归属整理；群是沟通场所 |
| 同一公司有多个联系人 | 先分别归档；公司关联需要明确来源，不按相似名字合并人 |
| 发送者身份缺失 | 保留原始记录并标出身份缺口，待修复来源，不制造匿名客户 |

群与人的成员关系可以用于资料归集和查找，但不产生白名单继承关系。

### 2.2 消息保留一次，关联可以有多个

原始消息按稳定来源标识归档，重复同步保持幂等。客户档案引用这些记录，不复制出另一份可独立修改的聊天。

群里一条服务商回复可能与某个客户有关；应与对应请求、引用消息或同一订单的上下文建立关联。不能因为一位客户在群中出现过，就把整群的货量、报价和发货都算到他名下。

资料归集原则：

- 私信保留双方完整往来，从首次接触开始。
- 群聊保留完整原始记录；客户资料纳入能关联到该客户的连续沟通，以及理解这些内容所需的上下文。
- 引用、回复、明确提及和订单关联用于理解关系；无法确定的内容保留为归属未定的材料。
- 不做“有价值／无价值”的原文删除。资料关联与结论提炼分别处理，不能靠提前扔掉消息提高表面整洁度。

## 3. 微信资料接入

### 3.1 原始资料、附件本体、识别结果分别保存

| 内容 | 归档内容 | 档案如何使用 |
| --- | --- | --- |
| 文本 | 原文、发送者、会话、时间、消息ID、修订 | 直接用于理解与引用 |
| 引用／回复 | 回复正文、原引用信息、双方身份及关联 | 还原问题与回答，避免单句误判 |
| 图片 | 原消息、本机可获取的图片、原图／缩略图标识、资源校验信息 | 识别文字与表格，引用时能打开对应图片 |
| 文件 | 文件名、类型、大小、原消息、本机可获取的原件 | 按文件格式抽取正文或表格，保留页码／工作表位置 |
| 尚未支持的消息类型 | 原消息类型及已有元数据 | 明确未理解，后续可补充处理 |

下载附件、读取附件内容、理解附件业务含义是不同的完成状态。不能因为消息被扫描到，就显示附件已经读懂。

产品需要显示：原件可用、仅缩略图、未下载／本机缺失、读取失败、待解析、已解析；失败时有具体原因和重试入口。附件缺失不会把整位客户变成“无需求”。

常用附件优先验证：价卡截图、报价表、货品清单、装箱资料和发货／轨迹截图。PDF、Excel、Word等文件格式根据实际样本逐项验收；不把“能下载文件”直接承诺为“所有格式都能正确解析”。

图片与表格中的金额、计价单位、货量、时效、邮编、有效期、适用条件必须保留上下文和位置。无法可靠识别的字段标记待核对；无需用户先逐张手动抄录，才能开始整理其他已有资料。

### 3.2 已核对的上游能力与实机验证边界

以用户此前提供的 wx-cli 0.7.4（`7bed9e7`）源码为基准：

- REST接口包含会话、联系人、消息和媒体读取。
- `/api/v1/media`具有图片、语音、视频与普通文件的处理分支；普通文件可以返回本机附件本体，取决于可用元数据与本地文件。
- 图片响应区分完整图与缩略图，优先使用本机已下载的完整图。
- 源码包含群成员数据读取能力，但公开REST路由未单列成员接口；不能默认联系人接口会完整提供群成员。成员覆盖需单独验证接入方式。

这些结论是上游源码能力核对，尚未在用户Mac上逐项验收。缺少本地原件、解密条件、附件定位信息或源端可见权限时，应用不能保证成功取得附件，也不承诺找回已删除或从未同步的历史。

- [媒体读取与普通文件处理](https://github.com/pandorafuture/wx-cli/blob/7bed9e7/crates/wx-cli/src/cmd/serve/media.rs#L188)
- [公开REST路由](https://github.com/pandorafuture/wx-cli/blob/7bed9e7/crates/wx-cli/src/cmd/serve/routes.rs)

### 3.3 名称必须能定位

联系人备注、昵称与群名在接入阶段读取，不依赖模型分析后补全。会话列表与联系人列表使用同一份来源身份数据。

名称读取失败时，该行仍应提供稳定会话ID、类型、最近消息日期、最近消息预览及来源详情入口。标明是源端缺少名称、查询失败或尚未读取，并可重试。不能只堆出一屏无法辨认的“待同步群名”。预览只供本机用户定位，不代表该消息已完成业务分析。

只有ID而无可读名称的资料继续保留；模型不能猜人名或群名。用户可添加本地显示备注，并标明是本地备注。

微信来源隐藏规则与本应用的联系人白名单分别说明。上游未暴露的资料不能被标成已完整采集；应用不自动改写上游隐藏配置。

### 3.4 接入完成的证明

界面区分源端发现、已归档、存在缺口和附件可用状态。采集检查需能核对数量、时间范围、来源ID和抽样原文，重复同步不会重复计数。

首次历史与后续新增共用归档；保留一个手动文件导入入口作为补充。导入记录必须携带足以关联联系人、会话和来源的信息，不能按文本相同就跨来源盲目去重。

## 4. 联系人级白名单

### 4.1 已确定的规则

白名单只有联系人这一种对象，每位联系人只有一个全局参与整理状态：参与整理或免整理。

- 同一人在私信、群聊和不同昵称下的状态一致。
- 名单内联系人不作为独立目标建立客户档案，不在客户列表中出现；原始聊天和附件保留。
- 在正常客户沟通中，名单内服务商或同事提供的相关报价、答复、发货信息仍可作为该客户的上下文与证据，不能把这些答复一起过滤掉。
- 工作账号本人作为“我方”保留发言，不建立为客户。
- 没有群级白名单、群成员自动继承、私信会话单独排除或来源优先级规则。

这替代此前群聊与成员联动的方案。

### 4.2 管理交互

在一个联系人管理入口中切换“参与整理／免整理”，共用搜索、来源查看与批量选择。

每行显示：备注／昵称、必要时的微信ID、出现过的私信或群聊、当前整理状态。支持按姓名、别名、微信ID搜索，以及按来源群筛选。

批量操作只做两种：加入白名单、移出白名单。明确区分勾选本页和所选筛选结果，显示实际选中人数；默认不替用户选择未看过的联系人。

按群批量处理时：先筛选该群已识别联系人，选择具体人员，再保存到这些联系人本身。群内后来识别到的新成员保持默认状态，用户可再次筛选处理。

同一人也出现在正常私信时，不产生另一套权限。他被加入白名单后，在所有来源都免于作为目标客户整理；移出后统一恢复参与。批量结果显示实际改变与失败项，不能只改按钮文字而后台状态不变。

导入旧配置时，已有真实联系人的手动排除按稳定ID去重保留。旧群级排除只做一次联系人清单转换，供用户批量核对；保存后仅保留人物状态，不继续关联群规则。无法确定身份的记录列为导入缺口，核对前不擅自开启有关资料的整理。不能把旧群ID误当联系人。

## 5. 客户档案：先把内容做对

### 5.1 档案需要回答的问题

1. 这个联系人是谁，与我们是什么业务关系？
2. 他经营什么货、涉及哪些市场与仓库、有什么运输或服务诉求？
3. 从首次接触到现在，需求、报价、对接和发货发生了什么变化？
4. 现在正在沟通什么，哪些事情已经有结果，哪些信息仍不清楚？
5. 这些判断分别来自哪些聊天、图片或文件？

每位联系人一份档案，允许存在多个具体事项或备货批次。批次用于区分资料，不在本阶段生成行动规则或强迫每位客户进入固定销售漏斗。

### 5.2 输出结构

| 内容 | 输出要求 |
| --- | --- |
| 身份与定位 | 源端备注、昵称、ID、来源会话；公司／角色仅在有证据时填写 |
| 业务画像 | 货品、市场、仓库、货量、运输诉求、价格关注与合作背景；适用范围不同的条件分开记录 |
| 当前情况 | 用具体中文说明最近的实际需求、已有结果和仍未知的部分；带更新时间 |
| 具体事项／批次 | 分开记录需求、询价、回复、方案与执行进展；订单、柜号原样保存 |
| 沟通时间线 | 从首次接触开始，按时间整理关键事件和变化；可展开原文及相关附件 |
| 资料与缺口 | 关联文件、图片、解析状态以及缺失对哪些判断有影响 |

没有来源的字段留空或写“现有资料未提及”。“未知”不自动变成“初步沟通”，单份图片未识别也不应使已明确的发货信息消失。

### 5.3 先事实，后总结

整理分为三层，每层可回到原始资料：

1. **原始资料**：完整保留消息、附件、发送者、会话、时间与引用关系。
2. **事实记录**：记录谁在什么时间询问、承诺、答复或报告了什么；分清说话人、事项所属人、预计时间与实际发生时间；附来源位置和不确定项。
3. **客户档案**：围绕客户问题组织事实，形成业务画像、当前情况和时间线。总结不能覆盖或替代原始事实。

先用可完整读入所选模型窗口的真实客户资料做直接阅读基线。长历史需要分段时，沿连续对话与引用保留重叠上下文，覆盖每段相关历史；汇总阶段可回读原文。不能只依赖多轮递归压缩后的摘要来做最终判断。

模型输出后检查身份、来源引用、时间、数字、单位、运输方式与前后矛盾。结构校验保证引用存在，业务正确性另行回放验证。局部问题保留为具体疑点，不能把整个客户的已有信息全部丢进隔离区。

运输模式按现有业务范围处理海运、卡航、班列，不能擅自改写成其他模式。金额必须带币种、计价单位和适用条件；表格内容保留页码、工作表或单元格定位。

### 5.4 预期输出示例

**历史反馈中的 benny Lam 发货信息，应得到这样的事实表达：**

> 订单 ZTH20261103 已实际发车。11月6日的对话中，服务商答复已发出，系统出库登记滞后；同日轨迹通知写明11月5日已发车，并标记已出境。该记录属于同一订单的运输进展。现有片段未说明最终签收结果。

每句话链接到相应原文；原始运单号与时间完整保留，不把“预计3–5天到达新疆”当成已经到达。不从这段片段推断客户的货品、货量或以后是否还有新需求。

**历史反馈中的“卡航可以。然后海运呢”，应整理为：**

> 客户表示卡航方案可以接受，并继续询问海运方案。海运报价是否已提供，需要检查后续对话后说明。

如果后续已有海运报价，则记录已有答复；不能永远停在“仍在询问”。运输方式不改写成汽运，也不从这两句推断确定下单或已发货。

### 5.5 增量更新与纠正

新增消息进入同一联系人资料，并检查是否补充、解决或修正既有结论。保留“当时怎么说、后来如何变化”，同时明确当前采用的结论。

用户可以对具体字段或段落执行“纠正这条内容”，填写正确表述或指出归属错误。修改保留来源和记录，并约束后续整理；无需进入独立任务系统。修改显示名、整理范围和业务事实是不同操作，入口文案必须清楚。

## 6. 最小交互范围

基础版本先提供三个工作区域，可在同一应用中切换：

- 资料接入：源端连接、联系人／群名、归档与附件状态、缺口定位。
- 联系人与范围：统一联系人，搜索、来源筛选、批量加入／移出白名单。
- 客户档案：名单外联系人资料、当前情况、事项、时间线与附件，支持查看来源和纠正。

这是能力分区，导航和布局在内容验证后细化；不预先建一套复杂大屏或多个任务页面。先用真实客户样例验证信息是否足够、是否好读，再确定卡片、列和展开方式。

## 7. 实施与验证顺序

| 关卡 | 交付物 | 通过条件 |
| --- | --- | --- |
| A：真实资料可见 | 会话、联系人、原文、图片与文件的可浏览接入 | 同步幂等；可定位名称；原件可用与缺失状态真实；私信／群聊发送者可辨认 |
| B：联系人统一与范围 | 一人一条记录、跨来源查看、批量白名单 | 同人跨私信／群不重复，同名不同人不合并；加入／移出在所有来源一致生效；相关服务商答复仍能支撑正常客户事实 |
| C：小样本档案验证 | 真实客户原文阅读基线、事实记录、档案样例和逐项评估 | 已发货等关键事实能准确提取；重要结论有来源；字段具体，疑点定位明确 |
| D：批量与增量 | 复用验证过的整理方法处理更多客户与新增消息 | 原始历史不丢失；新增回复正确更新当前情况；用户纠正不被覆盖；恢复和失败信息可理解 |

每个关卡先验收实际结果，再扩大范围。A、B不调用模型；C先验证效果，D再运行全量。模型业务效果不合格时调整资料组织、提示和模型选择，不用增加人工确认页面来代替质量改进。

### 7.1 样本与判定方法

先选择约10位有代表性的真实联系人：跨私信／群聊、仅群聊、明确已发货、存在多次需求、包含图片价卡、文件报价、长历史、服务商与商家混聊、资料不足等。选另一组未参与调试的联系人复测。

为每位样本人工标注一份精简标准答案：联系人身份、必须保留的关键事实、正确时间顺序、当前情况与原文位置。一次性建立验收样本，不要求用户在日常使用中重复完成这项标注工作。

记录：重要事实提取正确率、重要事实遗漏、跨人误归属、状态和时间错误、附件信息覆盖、纠正后回归。业务正确率的分母和待核对项都需保留；不能把错误内容删除后用“没有结论”冒充准确。

已提供的明确发车／出境样例、海运误写、同人跨会话、同名不同人、白名单成员重叠作为固定回归：重复客户、跨人串资料、把已发车写成尚未发、把海运改成汽运应为零。所有重要展示结论必须能定位到实际来源。

模型没有真实跑过的结果、合成模型测试和合法JSON都不能标记为业务验收通过。附件原件和群成员覆盖单独记录源端限制，避免把来源缺失与模型理解失败混为一谈。
