# 半托管欧区备货用户助手：产品方案

更新：2026-11-10，v0.12.1。当前已实现边界见[当前交付](README.md)，具体操作见[部署SOP](DEPLOYMENT_SOP.md)。本文收口此前多轮重建设计；旧实现仅供兼容，不作为新客户状态的来源。

## 业务目标

用户是跨境电商平台的产品／运营，通过个人工作微信向商家介绍欧区半托管备货、头程价卡和活动，拉群协调商家与服务商。助手帮助理解客户从首次接触开始的全部已归档线索，维护客户资料和每批备货进展，回答“今天该联系谁、为什么、怎么找到他、该说什么”。

主流程：**持续归档 → 按真实联系人归集完整相关私信与群聊 → 分册整理全部信息 → 总结客户、批次和未完成义务 → 人工处理关键确认与今日联系 → 实际回复、人工记录更新同一档案**。

先保证来源完整和状态可信，不用任务数或模型请求数替代业务成效。不做按“价值”提前过滤、不要求用户手建商家和项目、不增加复杂经验学习。

## 客户、批次与行动

| 对象 | 定义与规则 |
| --- | --- |
| 客户 | 工作账号＋稳定微信联系人ID，一人一份档案，私信与群聊归集。名称由微信备注／昵称提供，不能由模型猜。确认商家才进入客户列表；同名不合并，不自动按公司合并 |
| 初步沟通 | 介绍、触达、兴趣、顾虑、资料、约定和暂无需求等客户级内容；没有具体批次时仍完整保留 |
| 备货批次 | 一次具体备货需求及进展，原文证据和稳定ID关联；同一客户可以旧批已走货、新批待报价 |
| 下一步 | 有依据的我方义务或明确回访，不因“有聊天”自动生成。每项属于客户，可属于具体批次 |
| 关键确认 | 仅处理影响当前新增需求／未完成义务的歧义；按客户归纳、按批次和问题类型保存，解决后不因换说法重复提出 |
| 人工跟进 | 已联系、已收到反馈、暂未回复或备注；不等于实际发货。可单独记录，也可关联待办、改变状态和下次联系日期 |

批次阶段为：**需求确认 → 报价沟通 → 商家决策 → 备货中 → 已走货／已报告发货 → 已结束**。允许证据支持时跳转；“初步沟通”是客户资料，不是必须建立的空批次。

- “预计明天发”“预约卸货”“下午出唛头”属于计划或履约线索，不能凭一句预测宣称完成。
- 同一订单后续明确“发出去了”“已发车”“已出境”，应记已走货，系统晚登记出库不能把实际发车改回未发。
- 运单／柜号及卸货位、车牌、轨迹、头程邮件等后续对接应归旧批履约；不生成新的催备货、件重常识确认。
- 已走货关闭该批失效行动，不把整位客户结束；后续独立新需求仍进入新批。
- 人工确认批次阶段和依据后优先保留；可明确恢复自动判断。模型不自行覆盖人工决定。

## 页面与每日使用

| 页面 | 主要内容 |
| --- | --- |
| 今日 | 今日到期、后续安排、等待回复、已完成，按客户聚合；点击进入批次与行动 |
| 客户 | 只展示商家，搜索姓名／备注／来源群，按批次阶段筛选，每页最多50人；白名单人物不展示 |
| 客户详情 | 资料概览、批次与行动、完整时间线、人工跟进四个页签。每条线索、批次、行动、确认独立卡片，证据在卡片内展开 |
| 待确认 | 客户级入口，解决身份和影响当前行动的关键疑问；不把每条原文变成确认任务 |
| 整理与进度 | 自动开关与客户进度；最新倒序、每页20条、隐藏已完成、单客户暂停／继续／重试。可搜索并手动分析一人 |
| 会话范围 | 正常跟进／免跟进白名单分tab；会话／人物分开管理，搜索、每页50条。正常行只能加入，白名单行只能恢复 |
| 设置 | 账号连接、名称同步、wx-cli与后台监控、DeepSeek分析授权、七天用量、一个可选文件导入入口 |

待核实推断可以对照来源编辑、确认归属后保存为人工核实资料，或不采纳；处理记录可撤销。核实资料不直接打开任务或改变发货状态。分册使用可收起的本地浏览入口，SELF显示为我方，原文保持原样。

草稿仅围绕当前可处理的行动生成，记录同一用量台账，引用原文。用户编辑、复制并在微信发送；生成或复制草稿不会标记已联系。实际操作后在人工跟进记录结果，关联待办时可选择保持、等待、完成或取消；原文与结果历史保留。

## 排除、暂停和授权

| 状态 | 客户展示 | 来源分析 | 联系建议 |
| --- | --- | --- | --- |
| 正常商家 | 显示 | 已授权范围内整理 | 按有依据的义务 |
| 暂停联系 | 显示并标记 | 继续维护资料 | 暂停 |
| 人物白名单 | 不作为客户展示 | 本人私信只归档；正常商家群中的发言可作为其他客户的上下文 | 不以此人为跟进对象 |
| 会话白名单 | 该会话不产生客户结果 | 整会话只归档 | 该来源不产生建议 |
| 已走货旧批 | 客户仍显示 | 保留履约历史 | 该批不催新备货 |

模型不能修改白名单或外发授权。已有白名单持久保留；新会话是否继承授权由账号设置决定。源端名字不足应提示同步，不用模型命名填空。

任务计数、卡片状态与可用按钮由同一份后端投影给出：未开始／排队显示开始或继续，实际运行才显示暂停，正在启动／暂停时禁用重复操作。全局关闭不代表每位未开始客户都被手动暂停；选择一人仍可单独开始。旧running记录没有活跃锁时回到待开始／待继续。

单客户暂停分析只停止该客户的整理，已整理分册保留；与暂停联系建议独立。完成任务从进度列表移出，档案保留。文本整理和草稿不设每日Token预算门槛，保留用量统计和失败重试保护。

## 完整性与图片

“全部”指本地已归档、已授权的相关会话；不承诺隐藏、删除、未同步微信历史。按近15天活跃联系人优先排队，但每位从完整历史开始，不截掉早期线索。分片是传输单位，不是客户理解边界；分册、原文和历史版本可追溯。

图片可在本机预览，按需本地OCR生成候选；用户对照原图核对文字后，带版本的核对文本才进入下一轮分析。未安装识别工具也可手填核对文字。原件不发给DeepSeek，原聊天不改写。图片有布局、价格条件等未识别信息时仍保留覆盖不足提示，不把OCR当完整理解价卡。

## 交互与视觉约束

使用系统字体、系统深浅色、低对比背景、实底圆角卡片和明确的单一主操作。今日、客户、待确认、整理、范围、设置共用导航。宽屏侧栏说明固定底部，短窗口菜单独立滚动；窄屏横向导航与全屏详情，不挤压控件。

- 同组页签按内容宽度紧凑排列，不用space-between拉开；抽屉四个页签保持等宽等高。普通操作组16px间距，窄屏10px；搜索输入、筛选、提交按钮等高且底边对齐。
- 下拉统一主题浮层，支持方向键、Home／End、Enter、Esc与点击外部关闭，不被抽屉裁切。选中、禁用和焦点状态清楚可见。
- 每条线索、批次、行动和确认独立卡片；证据在当前卡片展开，加载中也可收起分册，返回保留搜索与筛选。SELF在派生展示为我方，原文不改写。
- 异步操作显示忙碌，服务端确认后再提示成功；失败保留输入，版本冲突要求重新核对。暂停分析和暂停联系明确区分：前者停止整理任务，后者仍维护资料但不推荐联系。
- 转场约120–220ms，以颜色、淡入和小幅位移为主；遵循prefers-reduced-motion。键盘可完整操作、触控目标尽量不小于44px，320px宽不横向溢出；状态不能只靠颜色传达。

## 效果验收

先抽查约20位真实客户，由人工按完整时间顺序标出身份、批次、状态、未完成义务及来源，再比较模型结果；不以合法JSON、任务数或模型自报confidence作为效果证明。

| 必测场景 | 预期 |
| --- | --- |
| 同人跨私信／群、同名不同人、改备注 | 稳定联系人归一，同名不合并，备注从源端更新 |
| 仅发价卡／寒暄、无具体需求 | 保留初步沟通，不制造兴趣、空批次或默认催办；“好的”等回复须结合上下文 |
| 群内多个商家与服务商 | 按人归属，不能把整个群当客户；白名单人物不进入客户和今日 |
| 跨群报价回复、同批多次改述、多批相似需求 | 同批关联，已回复不继续催，新批独立；重放不重复建义务 |
| 计划发货／预约与实际发车、出境并存 | 后续实际状态优先，已走货旧批不催备货，独立新需求继续处理 |
| 件重、柜号、车牌、卸货位等履约细节 | 记录旧批后续对接，不制造新需求或无意义关键确认 |
| 人工修正、完成、改期、暂停和名单变更 | 后续重试遵守人工决定；旧响应不能覆盖新操作，今日与详情一致 |
| 图片未识别、来源缺失、修订、未读新回复 | 明示覆盖不足，不推断无需求／确定报价；旧引用失效并等待重新整理 |
| 分册异常、重启、暂停后继续和快速切换 | 不丢原始资料，不复发已完成分册；控制版本阻断旧轮次发布 |
| 复制草稿、记录已联系、确认发货 | 三个状态分别记录；原文中的指令不能增加模型权限 |

扩大试点的拟定门槛：来源结构可追溯100%，受推荐客户可定位100%，归属正确率至少95%，行动准确率／关键行动召回／批次阶段至少90%；必测样本中重复义务、严重串客与错误报告已发货为0。以上是目标，尚非实测成绩。报告分母、缺失、误判与漏判，不能只输出“无需行动”来提高准确率。价卡有效期与激活匹配在后续交付时单独验收。

## 后续交付

下一步以真实客户回放校准商家归属、订单关联、发货与独立新批识别，并根据实测调整提示词和契约。随后再做有效价卡／活动驱动的历史激活、表格素材结构化和更细的媒体依赖判断。当前不引入长期经验学习、多Agent、向量库或自动微信发送。
