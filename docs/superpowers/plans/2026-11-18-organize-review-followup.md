# M3 整理链路审查修复计划

**状态**　workflow-v4 已完成云端开发。下列任务记录本轮设计与测试目标，已运行用例和兼容边界见[验收记录](../../verification/organize-review-followup.md)。基线为 `cdf72d7`、workflow-v3、schema 18。按下列顺序串行实施，完成云端回归后进入 M3 附件获取与解析。真实微信和模型质量在 Mac 单独记录。

**目标**　让已验证的事实可靠进入档案，让失败的长历史任务在恢复后取得新进展，并降低零变更整理的本地开销。沿用 Python、SQLite、现有 worker 和 React 整理记录。[上轮交付与验收](../../verification/organize-reliability-v3.md) · [模型执行方案](../../MODEL_EXECUTION.md)

## 1. P1　每条合并路径都核对候选事实及其证据

- [ ] 在 `tests/test_analysis_reliability.py` 增加普通整档、按字段、递归及缓存命中四种回放。两个来源分别报 12/kg、15/kg，模型仅返回前者时，应保留两个报价和各自的来源，或明确合并失败、保留旧档案。另测两个批次只返回一个、两条报价互换来源、相同报价由两条原文支持。
- [ ] 修改 `analysis/history.py`、`analysis/facts.py`、`analysis/reduction.py`（后端路径均相对 `src/wechat_agent/`）。让常规合并、递归合并和缓存结果共用逐候选核对；同值去重时并集证据，异值逐项保留归属。模型合并缺项时优先用已验证候选确定性组装；无法表达的冲突进入诊断并保留旧版本。
- [ ] 使旧策略的合并缓存与“输入未变”捷径失效，确保已受影响的档案下次整理可重算。保留用户人工覆盖和历史版本。通过生产 worker 测试验证发布内容、来源跳转和修复后的再次跳过。

## 2. P2　保留沟通状态和最近业务时间

- [ ] 在同一测试文件构造一个“询价中”的已知摘要，带有效原文时间。强制走本地合并，断言摘要状态、标签、时间和来源完整往返。再覆盖乱序多段、互斥标签、旧档案有标签而新结果漏字段。
- [ ] 在 `analysis/reduction.py` 的 `combine_field` 和 `preserves_candidate` 中补齐沟通元数据语义。单候选原样保留；多段选择有证据的最近业务时间。按业务时间处理状态变更，同一时刻互斥且无法判断时保留待核对提示。校验最终发布的档案，避免空值覆盖已有有效信息。
- [ ] 连同任务 1 运行 `.venv/bin/python -m pytest -q tests/test_analysis_reliability.py tests/test_history_workflow.py tests/test_profile_workflow.py`，新增冲突及历史兼容用例应全部通过。

## 3. P1　续跑从尚未完成的拆分节点推进

- [ ] 在 `tests/test_history_workflow.py` 构造至少 9 个各需拆分一次的父段。第一轮用完 8 次细分额度后可继续；重启 worker 并继续，断言第 9 个父段被拆分、成功子段新增模型请求为零、最终主材料覆盖恰好一次。
- [ ] 修改 `analysis/history.py`、`analysis/refinement.py`、`analysis/checkpoints.py`。按账号、客户、父请求内容和策略版本查回原细分关系；跨操作重建本轮覆盖关系，校验原文修订、范围和子段边界。只有首次生成的细分消耗本轮额度。用尽当轮额度且还有可推进节点时沿用“继续整理”；达到单节点深度限制时记录具体原因。
- [ ] 测原文修订、首次保存子段后进程中断、连续点击继续。失效子树重新计算；已验证兄弟子树复用；同一次继续仅创建一个后继任务。

## 4. P1　供应商恢复后允许显式重试

- [ ] 在 `tests/test_history_workflow.py` 和 `tests/test_operation_reports.py` 回放连续 429、连续 503 以及恢复后 200。保留原有每轮调用上限；冷却内重复点击不发请求；冷却后由用户显式重试，只有失败单元产生新调用。
- [ ] 修改 `model/gateway.py`、`operations/service.py`、`operations/reports.py` 及前端整理记录。持久化可重试失败类型、下一次允许时间与尝试轮次；优先采用有效 Retry-After，缺省沿用有上限的退避策略。保留累计审计和每轮执行预算，对鉴权失败、永久参数错误、证据越界分别给出对应操作。
- [ ] 联测并发双击、重启后冷却仍有效、混合临时和永久错误、旧检查点已耗尽 6 次。历史状态不足以区分原因时显示诊断，避免自动重置所有单元。浏览器测试核对提示、按钮和后继记录。

## 5. P2　零变更时复用冻结快照

- [ ] 在 `tests/test_context_snapshot.py` 和 `tests/test_analysis_reliability.py` 回放 1、1000、10000 条消息。连续运行两次，记录准备阶段耗时、附件查询数、快照行数与正文总字节。第二次无变化时，断言无新正文副本、无逐消息附件查询、无模型调用。
- [ ] 修改 `context/builder.py`、`analysis/runner.py`。在同一一致性视图内用轻量材料清单比较最近可复用快照，包含截止时间内可见消息及修订、会话范围、参与人、附件状态、来源缺口、人工资料及模型／策略版本。新鲜度校验仍覆盖发布前的并发变化。将本轮执行与冻结材料的标识分开，避免复用旧快照时误用旧操作的 `history_runs.operation_id`。
- [ ] 首次及有变化时按会话批量读取附件；旧 schema 18 数据在首次缺少可验证清单时走原路径。逐项改变输入，各验证失效；另测两账号同联系人、截止时间跨过一条消息、并发人工编辑和中途重启。
