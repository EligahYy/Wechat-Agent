## 共同依据与边界

- [产品方案](../../PRODUCT_DESIGN.md)、[交互方案](../../INTERACTION_DESIGN.md)、[模型执行方案](../../MODEL_EXECUTION.md)、[实施方案](../../IMPLEMENTATION_PLAN.md)。
- [内部接口约定](CONTRACTS.md)只固定本应用内部名字和形状；上游协议在 M0 通过适配器映射。每份计划注明它创建和消费的契约。
- 文件按功能放在 `src/wechat_agent/`，测试位于 `tests/`；前端为 `frontend/`。原型 `ui-prototype/` 保留为参照，不把它的示例任务当生产代码。
- 后端 Files 中的 `api/`、`source/`、`profiles/` 等短路径均相对 `src/wechat_agent/`；tests、frontend、docs、scripts 路径相对仓库根。花括号表示同目录下逐个创建列出的文件；不允许借此省略实际消费的文件。
- Python 3.12、Node 24；依赖版本在各阶段实际安装解析后生成锁文件。Python 使用 `requirements-dev.lock`，前端使用 `package-lock.json`；此刻不手填不可验证版本。
- 运行数据放本机应用数据目录；`.local/` 存临时证据，均不入 Git。真实聊天只在本地，脱敏且复核的测试材料才提交。
- 每个任务都先运行其失败测试，再最小实现，再验证。纯 Mac 人工核验直接记录证据，不为命令行说明编造单元测试。
- 所有开发、修复及自动测试在云端完成；每个任务检查通过后直接提交推送 main，用户本地 pull 验证。当前只完成 M0 第一个任务，不把待验证结果当实机通过。
- 测试代码片段列出关键断言；文件顶部导入相应 pytest／HTTPX、Testing Library 或 Playwright，夹具由对应任务创建。它们是待实现测试，不代表现在能在仓库运行。

## 云端继续执行

云端使用 `executing-plans` 逐个任务实施，维护代码、回放测试和验证命令，检查通过后推 main。用户不需要在 Mac 上编写代码或执行开发计划，按 [Mac 验证指南](../../MAC_SETUP.md) pull 并验证即可。

阶段状态分开记录：`cloud_development`（未开始／进行中／已完成）与 `local_validation`（待验证／通过／失败／不支持）。源端或模型协议未知时先实现明确契约、配置校验和回放路径，未支持处如实报错；收到实机报告后在云端修正，不能猜协议或伪造真实成功。

[M0开发与验证报告](../../verification/m0-report.md)记录当前范围、证据及取舍。
