# 实施与验收计划：真实微信采集 + DeepSeek API

状态：开发计划，所有命令均为拟实现接口，当前不可执行。目标是先验证真实微信采集与 DeepSeek 两个关键依赖，再在本地形成可恢复的商家备货业务闭环。应用本地部署，获准上下文通过 API 外发。

## 1. 开发顺序

### M0：关键依赖接入验证（首个关口）

在真实 Apple Silicon Mac 核实候选 wx-cli 兼容矩阵、可接受权限、私信／群全文、稳定 ID、方向、分页及分片状态；在 DeepSeek 用虚构片段验证模型权限、JSON 参数、usage 和有效响应。无可接受采集路径时明确阻塞，不将导入样例验收替代实时接入。密钥仅安全配置，不能贴入聊天或文档。

通过条件：两个依赖分别有真实结果和版本记录；遇到权限变更或缺少 API key 时完成独立开发，但不声称集成就绪。具体准入见技术架构和 DeepSeek 文档。

### M1：采集、导入与存储

实现项目骨架、锁文件、迁移、JSONL 校验、会话白名单、消息幂等入库和虚构样例。样例覆盖两个商家、两个头程服务商、同商家两批备货、私信、三方群与混合商家群，另含虚构海报说明和结构化价卡。

通过条件：重复导入不增重复消息；同样内容的不同消息仍分别保存；坏记录可定位；来源和覆盖范围可见；不需要微信或模型启动。

### M2：商家备货业务闭环与 DeepSeek 接入

实现商家／服务商角色关联、价卡与素材版本、备货项目、人工事实、任务状态机、三方卡点、今日清单、联系记录、机会录入及规则草稿模板。

同步实现外发策略、脱敏别名、DeepSeek worker、响应 schema／证据校验、人工建议审核和调用预算。规则仅做硬约束与故障降级，不替代计划中的 DeepSeek 语义分析。

通过条件：可从样例完成“价卡审核 → 匹配商家 → 人工确认触达 → 建立备货项目 → 关联人工三方群 → 分配卡点 → 确认计划 → 记录并核验节点 → 安排下一批跟进”；用户编辑不会被重放覆盖。

### M3：端到端可靠性与真实设备联调

将已验证 collector 接入同一业务库，先检查真实消息在本地归档，再预览获准的真实外发上下文；确认后启用 DeepSeek 项目增量分析。真实设备测试不能由 Linux 云环境代替。

通过条件：私信／群正文、身份、方向、批次正确；断网、休眠、重启、翻页与分片异常可恢复或显示 gap；DeepSeek 失败不阻塞采集；用户修改受保护。检查过期／内部素材过滤、三方责任、真实 token 与输入输出质量。

### M4：日常试运行

先选择约 10 家商家试运行一周，包含活跃、待成交、历史客户；该规模仅为建议。每日记录有效建议、误报、漏项及整理耗时，按实际结果调整规则。

## 2. 预期本地操作方式

以下命令是后续 CLI 的实现目标，仓库目前没有对应程序：

```bash
# 工作目录：Wechat-Agent 仓库根目录
uv sync --frozen
uv run wechat-agent init --timezone Asia/Shanghai
uv run wechat-agent import tests/fixtures/demo.jsonl --preview
# 在界面或 CLI 明确选定样例会话白名单后再正式导入
uv run wechat-agent import tests/fixtures/demo.jsonl

# 完成 M0 后，分别运行 API、采集进程与 DeepSeek worker
# 凭据通过本地钥匙串配置，不在命令中填写真实值
uv run wechat-agent source validate --source wx-cli
uv run wechat-agent model validate --fixture tests/fixtures/deepseek-smoke.json
uv run wechat-agent collect --source wx-cli
uv run wechat-agent serve --host 127.0.0.1 --port 8765
uv run wechat-agent worker --engine deepseek
```

init 默认使用 macOS Application Support 下专用目录，配置非机密路径可覆盖；不写入微信数据目录。启动页面提示需要的本机会话登录方式。启动前检测端口冲突，不结束其他用户进程。

模型模式明确配置官方 DeepSeek endpoint、已验证的模型 ID 和 Keychain 凭据引用；不回退到其他供应商。健康检查同时展示 worker 心跳与分析引擎状态，仅有监听端口不视为就绪。

## 3. 必须验证的故障与边界

| 场景 | 预期结果 |
| --- | --- |
| 同文件导入两次 | 新增为零，任务与建议无重复 |
| 同文本／同秒不同 ID | 均保留，不误去重 |
| 缺 ID、无时区、非法方向 | 拒绝或隔离，并指出记录位置 |
| 同昵称不同联系人 | 不自动合并 |
| 混合商家群 | 模糊归属进入待确认，不自动给所有商家建任务 |
| 历史消息写“明天” | 依据原消息时间，不能按今天解释 |
| 历史已过期待办 | 默认待复核，不直接成为今日正式逾期 |
| 任务后续改期／取消 | 建议更新既有任务，用户确认后保留变更历史 |
| 用户修改后重新分析 | 不覆盖修改；冲突可见 |
| 点击复制但没发送 | 无已联系记录 |
| 联系后事项未解决 | 联系记录已更新，业务任务仍保持待办或等待客户 |
| 激活客户拒绝联系 | 候选被排除，不能靠模型绕过 |
| worker 在提交前后退出 | 租约可回收，重跑无重复正式任务 |
| 模型返回坏 JSON／假消息 ID | 校验失败，不污染客户事实 |
| 聊天里要求执行命令 | 作为文本，无工具执行 |
| 上游只有 snippet／分片失败 | 显示 partial／gap，不标成完整归档 |
| 分页期间补入历史消息 | 回查幂等合并，记录无法保证的覆盖范围 |
| 恢复备份 | 商家、消息、任务、人工修改及来源可用 |

## 4. 质量评估

先人工标注一组获准使用或虚构的样例，覆盖明确需求、闲聊、拒绝、引用、日期歧义、多个承诺和状态变更。记录评估集版本，禁止混入提示词样例再宣称泛化效果。

- 待办精确率：建议待办中真正需要处理的比例。
- 待办召回率：人工标注待办中被正确发现的比例。
- 来源可追溯：正式任务必须有可检查证据或标注为人工创建。
- 日期正确率：明确日期与歧义保留分别检查。
- 重复／错误归属：跨批次及跨商家单独统计。
- 草稿可用性：可直接采用、需小改、需重写、存在事实错误分别记录。

建议试运行门槛：证据校验与用户修改保护必须全部通过；业务建议精确率目标先设 90%、明确待办召回目标 80%，属于待实测目标而非已达到指标。样例数量和分布一起报告，不用小样本百分比代替效果说明。

## 5. 每个里程碑的交付证据

保存所执行命令、版本、通过／失败／未执行项和必要的脱敏错误日志。不保存真实聊天作为仓库测试样本。

M0 提供两项真实依赖验证；M1 提供幂等采集／导入证据；M2 提供业务演示和 DeepSeek 结构化评估；M3 提供设备覆盖与端到端恢复记录；M4 提供实际使用结果。只有 M3 通过才能声称支持持续采集到 AI 跟进建议的真实链路。

## 6. 本地跑通后的决策

DeepSeek API 已是确定分析方案，字段外发许可在真实调用前确认。一周试运行后再讨论独立常驻设备、远程访问、是否将应用迁移服务器、是否有多用户需求；这些扩展不作为首版前置条件。


## 7. 业务专项验收：平台备货与三方协同

以下均使用虚构业务数据和可识别的样例素材，不将真实平台内部价卡、海报或客户信息提交到 Git。

### 端到端演示

1. 导入某市场普通货头程价卡 v1 及宣传海报，人工审核有效期、计价条件和对外可用范围。
2. 商家 A 已表达该市场备货需求；系统建议联系 A。商家 B 货型不匹配，排除确定报价推荐。
3. 人工确认向 A 发送素材；A 表示“先看看”，仅记为了解／询价，不自动确认为备货计划。
4. 补齐 A 的货物与时间需求，建立项目 P1，匹配服务商 S1；用户人工建群，再关联群与项目。
5. S1 承诺核实附加费，A 承诺补装箱信息。生成两项不同外部责任的任务和我方检查日期。
6. 形成针对 P1 的确认报价快照，记录商家接受计划的证据；未确认条件仍显示待办。
7. 填写交货／发货／到仓的计划与事实。聊天说“已发”只记为对方反馈；平台完成口径尚未满足时，结果保持待核验。
8. 人工录入核验结果，结束本批；新建 P2 测试同商家多批次隔离。
9. 导入价卡 v2，验证旧报价不变、过期 v1 不再推荐，且仅口径可比时才显示价格变化。
10. 录入一个已解决的历史备货顾虑，验证可生成有依据的重新联系建议；暂停／拒绝联系商家仍被排除。

### 必测反例

| 场景 | 预期结果 |
| --- | --- |
| 服务商说“明天发报价” | 责任方为服务商，不建成商家发报价任务 |
| 已建三方群但未定方案 | 项目不能标为已备货 |
| 同群同时讨论两批货 | 不确定批次的消息进入复核，不复制到两个项目 |
| 多家服务商方案并存 | 分别保存，不把参考价当最终确认报价 |
| 价卡 kg 计价、旧卡 CBM 计价 | 条件不足不直接比较或算节省比例 |
| 海报价格与价卡冲突 | 停止确定性价格建议，要求人工核对 |
| 有效期不明、过期或仅内部使用的素材 | 不自动推荐对外发送／导出 |
| 复制后素材被撤回 | 再次复制／导出前重新检查；已手工发出的记录保留，不声称能撤回微信内容 |
| 商家回复“收到” | 不自动确认方案、发货或入仓 |
| 预计到仓日已过、没有物流数据 | 生成核实提醒，不断言物流延误事实 |
| 商家有未解决投诉 | 排除营销激活，保留服务处理任务 |
| 平台产品操作问题 | 进入产品问题清单并关联项目，不归为服务商失约 |

试运行统计分商家数、项目数和素材版本；BD 触达、三方对接、计划、发货、结果核验分别计数，不把群数量等同于转化。覆盖不全时报告 unknown，不能用零填充。业务结果不是一期自动采集或平台 API 对接已实现的证明。


## 8. DeepSeek 与实际采集的专项验收

- 未批准外发会话可归档但不得出现在模型请求；别名映射和微信 key 永不外发。
- wx-cli 退出时模型队列可继续处理，DeepSeek 超时／预算用尽时采集仍持续。
- 真实窗口完整分页、同秒多消息、跨分片与迟到补录不误去重；不可证完整时显示 gap。
- 同一数据重放、worker 崩溃重领和 API 重试不会重复应用建议；可能重复 API 计费明确报告。
- 价卡过期、海报撤回、用户改期后旧草稿失效，重新生成使用当前版本。
- 请求参数、finish_reason、usage 和模型名用真实虚构片段检查；mock 故障结果单独报告。
- 无原生图像能力时只处理人工审核的价卡字段，不把图片占位解释为已读取价格。
- 可追溯证据、任务责任方、日期与项目归属评估均通过后，才开启已批准真实范围的自动增量分析。
