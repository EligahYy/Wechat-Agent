## 执行结果与链路

1. 接入：保留绑定账号、固定来源版本、worker和鉴权检查。新版`.2`安装到独立目录，旧`.1`保留可回退；应用兼容两版。
2. 刷新：统一在sync_scope入口执行显式刷新，覆盖API全量、单联系人、资料刷新及CLI同步。原先仅refresh_contacts调用刷新，sync_and_organize直接check，来源failed后不能恢复。
3. 来源状态：外部数据库写入使已发布资料过期时使用stale，不再冒充刷新执行失败。stale不可归档，需成功刷新后读取；同步中途变化仍安全中止。
4. 请求竞态：接受HTTP刷新请求前原子标记running；已有running则合并到同一在途刷新，不额外排队，避免读到前一次failed或被旧任务覆盖。只认可稳定成功代次，不因202判定同步成功。
5. 归档：保留元数据页前后版本校验、应用health前后校验、游标、账号和会话租约；不放松来源缺口保护。
6. 整理：只有无来源缺口时进入模型，模型失败仍保留既有资料。模型配置不会修复来源失败。
7. 诊断：名称索引构建失败、版本读取失败、构建中版本变化输出固定错误码，不输出联系人或密钥。v2版本标识同步纳入联系人诊断字段。

Ruling：合并在途刷新意味着等待同一次稳定发布，而非强制在每个点击之后重新打开一次数据库；来源中途又变化仍安全中止并提示重试。成本：持续高频微信写入或后台重复刷新时，可能仍需再次同步；不以吞掉冲突保证成功。
