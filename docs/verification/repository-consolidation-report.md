## 来源问题结论

代码可以复现关联／筛选过宽：原先members表同时包含目录成员和实际发送者，只凭成员关系就把整群列为联系人来源。日历蓝点按全部群消息计算，即使当天本人0条也会标蓝。截图本身无法证明真实消息丢失，云端未读取用户数据库。

现在原文和日历复用同一范围：群聊必须已有该联系人当前有效、非系统的真实发言；私聊保留可验证双方关系，包括仅我方主动联系。仅成员目录的群不会出现在来源选项，也不进入全部来源结果。原始归档、模型上下文构建、联系人身份和业务范围不改写。

真实关联群里某天只有其他人发言时，仍保留当天上下文；灰点表示上下文，蓝点表示本人发言，并提供本人／会话条数提示。0/0不再由蓝点暗示为本人发言丢失。成员记录单独新增不改变来源，真实新增发言会使游标失效并刷新。

对应来源测试2项RED、1项已有私聊特征检查；3项GREEN；原文／月历相关31项通过，完整后端408通过。真实源端仍可能有未归属事件或采样覆盖不足，不以本次修复宣称所有微信名称／作者都已验收。

## 实施裁定及代价

1. 归档而非删除旧计划／原型；保留当前源码测试和迁移，不凭引用数量猜死代码。代价：历史目录仍占仓库体积，但不再混入有效入口。
2. 来源成员关系不再冒充真实沟通；已确认会话中其他人物上下文仍保留。代价：只有成员信息且本人发言尚未归档的群暂不展示，后续真实归档会自动纳入；不改底层历史。
3. 蓝点只表示本人发言、灰点表示会话上下文，最新定位保持当前归档语义。代价：颜色与含义改变，旧截图不能作为新口径。
4. 文档过时端口／原型指引虽被审查标Minor，本次目标就是清除此类误导，按必须完成项修正。代价：活跃说明重写，旧措辞在历史快照及Git保留。
5. 实机证据仅承认用户回传，能力和质量未确认仍待验证。代价：后续真实样本可能要求追加修复，不能以云端绿色替代。
