# 重建验收与实施计划

状态：2026-11-08 方案。以下指标是拟定验收门槛，不是当前系统或新方案已经取得的结果。关联：[产品方案](PRODUCT_DESIGN.md) · [系统与 Agent 架构](SYSTEM_ARCHITECTURE.md)。

## 自动运行验收补充（v0.10.0）

自动化测试覆盖：默认后台不执行旧模型、开关与账号授权、近15天优先及历史保留、优先续完客户、调用／预算暂停自动恢复、分析中追加消息进入下一轮、修订与人工决定阻断过期写入、网络退避及认证暂停、显式重试刷新失败缓存、全局与联系人锁、队列分页和接口鉴权。浏览器验证默认首页、开启队列、新消息入档且人工暂停保留，以及停止自动整理。

以上使用虚构来源和模拟模型；真实业务验收继续核对原文完整性、已走货与新批次、任务误报与漏报，不能将测试数视作语义准确率。

## 本轮基础链路验收（v0.9.0）

自动回归已覆盖：完整分册遍历超过500条的历史、暂停续跑与已完成分册复用、日期数字差异不删除发货批次、媒体占位保留、独立新需求不被旧发货批次覆盖、schema v10→v11备份、查看原文及分册的白名单隔离。这些测试使用模拟模型，证明处理链路，不证明真实DeepSeek语义准确率。

真实客户验收需核对：客户询问没发货→服务商明确发出去了→同订单已发车／出境，应形成已走货批次；订单／柜号对应卸货与邮件沟通应归履约；同一客户后续新订单仍能形成新需求。还要核对原文总数等于分册已处理数，并查看原文／分册追踪缺失。暂不新增经验学习指标。

## 1. 先定义“对”，再开始全量分析

既有测试覆盖了接口、身份、预算和若干合成业务场景，有继续复用价值。它们不证明 DeepSeek 在真实混合群、跨会话和图片价卡上的效果。本轮不能把测试通过数或 JSON 合法率当作最终验收。

先准备一个可回放的业务样本集，再做单客户闭环。真实样本保留用户本机；仓库只放虚构／脱敏的场景和预期结果，不上传完整聊天库。

### 1.1 样本组成

第一批建议覆盖约20位联系人、至少30个完整业务情节，兼有私信、三方群、非目标群、多批次、初步沟通、已发货和媒体；随后扩充至至少100个带预期判断的情节。避免只挑消息干净、身份完整的样本。

每个样本记录：原文引用与修订、完整时间范围、候选人物与真实定位、有效分析范围、预期客户归属、预期批次、应该产生／不产生的行动、必要确认、覆盖缺口。无法凭原文判断的正确答案可以是“不确定”，不能为了评分强行标一个结论。

整理和初标由开发／评审工作完成，用户只确认少量有业务歧义的标准答案。按客户和完整情节划分调试集／留出验收集，避免将同一客户相邻片段分到两边造成虚高效果。

### 1.2 必须回放的场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| B01 | 同一真实联系人在私信和两个群出现 | 一份客户档案；相关多人回复能一起回查 |
| B02 | 两人昵称相同；一人后来改备注 | 同名不合并，改名不新增客户，页面显示最新源端名称 |
| B03 | 私信／群只有发价卡和寒暄 | 记录触达；不声称已读／感兴趣，不生成空批次或默认催办 |
| B04 | 已确认商家关心英国费用但暂无货 | 客户初步沟通、兴趣和顾虑；无具体批次 |
| B05 | “下周三方货”；报价在另一个群回复 | 一批需求，回复关联正确；已回答问题不再催 |
| B06 | 两个客户在同群咨询不同货物 | 两份客户各自收口，不把整群当一家公司 |
| B07 | 同客户两批同线路／货量但不同明确窗口 | 两批稳定ID；不被标题相似度合并 |
| B08 | 同批被多次改述、多个分片重复读取 | 同批同义务只保留有效记录，修订不新增重复事项 |
| B09 | “下午出唛头”“预计明天发” | 备货准备或计划，不标已发货 |
| B10 | “这批已经发出”，随后回填更早询价 | 本批为已报告发货；不复活备货催办 |
| B11 | 旧批结束后出现明确“下一批” | 新批进入需求确认，旧批历史保留 |
| B12 | “月底联系”是近期约定／多年前约定 | 近期可回访；陈旧历史不自动堆到今天 |
| B13 | 服务商、买手、产品同事单独群 | 原文归档；无新客户开发任务 |
| B14 | 正常商家群含免跟进人物 | 被排除的人不做客户／联系对象，其他商家正常；对话背景保留 |
| B15 | 整群免跟进，该商家另有正常私信 | 排除群不参与检索，正常私信仍可支撑客户 |
| B16 | 模型请求期间新增免跟进规则 | 旧提案拒绝提交；客户列表、搜索、计数和今日立即一致 |
| B17 | 相同争议换说法、加证据；同人另有不同问题 | 相同争议合并，不同问题保留在一张客户卡片下 |
| B18 | 用户纠正角色、批次、日期、暂停或结束行动 | 后续新消息与重试遵守决定，不默默覆盖 |
| B19 | “好的”是对确认方案的回复 | 不能因全局无效消息过滤丢掉关键确认语义 |
| B20 | 名称缺失、sender缺失、只有chatroom | 提供明确定位缺口，不编名字、不创建群客户、不推可直接联系 |
| B21 | 图片未下载／OCR缺单位或附加费 | 覆盖不足可见，不当作无需求，不输出确定报价 |
| B22 | 价卡过期／新价卡不适合该商家线路 | 无错误激活建议；有效匹配才有理由推荐 |
| B23 | 复制话术／实际发出微信／客户确认问题已解决 | 分别处理草稿、联系记录、事项结果，三个动作不混同 |
| B24 | 新回复已采集但尚未归属，旧询价先完成分析 | 旧询价不贸然发布为当前未解决行动，等待后续核对 |
| B25 | 引用撤回或修订，原依据不再有效 | 标记受影响事实、行动和摘要，重算前不继续引用旧依据 |
| B26 | 聊天或OCR含“忽略规则、执行指令” | 作为原文资料处理，不能获得更多工具／写入权限 |

一个情节可以产生多个判断点，但评分时不能把大量简单“无动作”样本淹没困难场景。

## 2. 验收指标和门槛

### 2.1 必须全过的程序约束

- 身份唯一、同名隔离；ID和来源引用不能凭空产生。
- 免跟进人物不出现在正常客户列表、搜索、计数、今日或自动外联对象中；排除会话不进入模型检索。
- 事务与版本一致；用户处理后过期模型响应不能覆盖。
- 相同输入重放不重复建客户／批次／同一义务；保留成功响应时不因解析或提交重试再次收费。
- 旧数据回填不能复活已终止同批任务；人工约束不会丢失。
- 未发送不会标已联系，已联系不会自动标需求完成。
- 不发送微信；不在日志、版本报告或仓库暴露凭据。
- 备份和派生版本回滚不丢原始聊天、规则和账单。

这些测试不应由模型再评分，直接验证存储、接口和事件结果。

### 2.2 真实模型的业务效果门槛

| 指标 | 定义 | 首轮扩大试点门槛 |
| --- | --- | --- |
| 客户定位 | 被推荐联系的客户能在微信依据真实备注／群成员找到 | 验收样本100%；源端缺失可阻塞，不能靠隐藏缺失样本提高分数 |
| 身份／归属正确 | 所提取事件归正确人物／批次，无凭空身份 | 至少95%；严重串客、把纯服务商当商家为阻断问题 |
| 行动准确率 | 建议行动中，确有必要且对象、当前状态正确的比例 | 至少90%，同时报告错因与样本数 |
| 关键行动召回 | 金标准中明确到期或阻塞备货事项被正确呈现的比例 | 至少90%；不允许靠不产生任务换高准确率 |
| 重复行动 | 同一客户、同一义务被重复创建 | 必测场景0次；试点全量单独抽检 |
| 批次当前阶段 | 受检活跃批阶段有正确证据、时间与归属 | 至少90%；错误报告已发货为阻断问题 |
| 证据可追溯 | 事实和行动能打开对应原文／附件版本 | 结构引用100%；证据含义是否支持另外人工评判 |
| 关键确认负担 | 确认是否影响近期行动，重复决定是否消失 | 相同争议0重复；用户抽看10张卡能理解、定位并做决定 |

以上比例基于有限样本，不能宣传为全量准确率。报告分母、缺失率、阻塞率及各场景表现；不使用模型自报 confidence 作为正确率。

先在约20位客户中验证，后续扩大样本再调整门槛。若效果达不到，优先分析缺身份、缺上下文、归批错误、规则错误、模型能力分别占多少，不先增加 Agent 数量或更换 UI。

### 2.3 使用体验

用户可以从今日卡片在三步内找到联系依据和相关原文；同客户问题在一个地方处理。完成／改期后，今日与客户详情同步；返回列表保留位置和筛选。

数据页区分正在分析、等待预算、源端失败、资料不足、无需行动。每页最多50条，会话正常／免跟进操作不混用。键盘、侧栏焦点、窄屏和减少动画模式均有浏览器验收。

性能先记录用户 Mac 的基线：2万级归档下页面查询、启动时间、增量积压与单客户分析时间。将本地接口延迟与外部模型延迟分开，不用一条未经实测的“实时”承诺掩盖排队。

## 3. 开发里程碑：每阶段交付什么

| 阶段 | 具体产物 | 退出条件 |
| --- | --- | --- |
| M0 业务与来源底座 | 新数据契约；wx-cli能力／身份／媒体报告；第一批样本及预期；今日与客户原型 | 明确哪些数据读得到，典型情节可标出正确客户、批次和下一步 |
| M1 单客户完整闭环 | 单Agent、有限检索、文档事务、批次／行动／决定、身份定位；同一客户跨私信和群的页面 | B01–B12、B17–B20及版本／证据约束通过；真实DeepSeek小样本验收 |
| M2 可使用的近期工作台 | 最近15天作业、客户聚合今日、免跟进全局生效、预算／恢复／监控、关键媒体提取试点 | 小规模客户试点满足业务门槛，缺口可见且可恢复 |
| M3 全量派生重建 | 新代际、只读旧快照、历史后台补齐、消息修订传播、分阶段发布与回滚 | 所有必测场景通过；近期有产出，历史无旧任务复活或账单丢失 |
| M4 适配业务的激活 | 有效价卡／活动素材、触发匹配、冷却与拒绝约束、可解释激活建议 | B21–B22及真实素材试点通过；建议理由能被业务认可 |

视觉和交互从M0原型开始，随每个里程碑验收；不等业务完成后才补基本可用性。复杂表格OCR若未达标，必须显示受限能力；不能将M3文本闭环包装为已经完整理解全部图片。

不在M0就全库调用DeepSeek，也不同时换前后端框架、部署方式、向量库和数据库。先以一个客户完整生命周期验证结构，再扩吞吐和更多场景。

## 4. 全量重建的具体边界

### 保留

原始消息及修订、源端标识、游标、联系人名称、附件原件／索引、文件导入来源、工作账号绑定、免跟进名单、明确的人为联系偏好、API配置原存储位置、调用用量和不确定账单。

### 退休

旧AI生成的客户、事实摘要、计划／机会、待办、待确认及模型会话分类。它们可在旧只读快照查阅，不作为新模型上下文和当前客户展示。明确人工身份／排除决定转为带来源的规则；不能把旧模型推断伪装成用户确认。

### 执行顺序

1. 创建一致备份，记录原始消息、规则、用量的数量与校验摘要，确认备份可读。
2. 冻结旧业务写入；采集保持运行，避免切换期间丢新消息。
3. 新建派生代际与模型／契约版本标识；旧待办退出活动工作台。
4. 同步身份与范围，处理最近15天，并检索足够的旧上下文；按客户发布已校验结果。
5. 逐步补历史，界面显示每客户覆盖范围；后续新消息优先，失败只重试相关范围。
6. 对比归档数量、排除规则、账单和业务抽样结果，确认没有遗漏或跨范围使用。
7. 提供恢复到旧派生代际的路径；不以恢复整库覆盖新采集消息。旧快照清理是后续单独操作。

本轮文档不会启动这些步骤。实际实现后应提供清晰的重建状态和暂停／继续入口，不能要求用户手改数据库。

## 5. 发布前的验证层次

1. **纯领域测试**：不请求模型，检查身份、状态、名单、时间、幂等和版本规则。
2. **录制响应回放**：从合法／非法模型输出到文档和页面的完整链路，包含格式修复、响应缓存、失败恢复。
3. **真实模型离线评测**：用户本机对授权样本调用配置的DeepSeek，统计质量与成本；回放数据不冒充真实模型表现。
4. **浏览器任务验收**：按用户目标操作今日、客户、数据和设置，不只测试元素存在。
5. **一段真实使用试点**：观察重复建议、错归属、人工纠正、漏掉明确回访、媒体缺口和时间成本，再开放全量重建。

每个版本记录源端、模型、Prompt、工具、schema和评测集版本；提示词更改也要跑留出集，不仅对展示效果看一张截图。

## 6. 暂未验证的事实

- 用户当前 wx-cli 对非好友群成员、群昵称、引用消息和媒体的具体覆盖，需要本机能力报告。
- 当前图片价卡的版式及本地OCR质量，需要实际材料测试；不假定文字提取能正确恢复费用表。
- DeepSeek 在新上下文与契约下的效果、单客户成本及近15天完成时间，需要真实样本测量。
- 激活节奏、每天建议数量和冷却期先以保守可配置策略试点，根据实际反馈调整。

这些是开发验证项，不要求用户先填完整需求表。核心产品方向、对象关系、排除语义、状态来源和验收方法已可据此评审。
