# 实施状态：v0.9.0 / 客户完整资料分析

更新：2026-11-09。当前阶段优先修复基础链路的覆盖与准确性；仍按联系人手动试点，尚未切换全库自动后台分析。

## 本次交付

1. **客户完整来源归集**：读取该账号授权范围内，目标联系人私信和出现过该联系人的群聊全部本地可见记录。保留问答、其他参与人上下文、图片及不完整文本占位；不按消息价值删选，不再截取每群500条或最后80条。群里其他人的内容不自动等同客户事实。
2. **分册整理后总结**：每会话按时间分册，每册通常最多32条／约10000 JSON字符；长单条独立成册。DeepSeek先整理事实分册，全部完成后才合并、生成客户档案并复核。大量分册做逐级合并，原始分册和原文均保留。
3. **预算内续跑**：一次操作最多新增12次模型请求；资料整理、合并、最终总结和复核均计入共用预算。达到次数或预算上限时保存进度并暂停，不发布尚未完成的最终档案。再次分析复用已验证分册和响应；初次历史较长可能需多次继续。
4. **减少破坏性过滤**：日期或数字差异改为字段待核对，保留独立成立的发货状态及原文；单个问题批次不连带删除其他批次。不能归属或运输术语冲突的推断保存在待核实区，不能作为已确认客户事实。
5. **可核对覆盖**：试点页显示已整理条数／来源总数、分册进度、合并／总结／暂停状态。客户详情可分页查看全部相关聊天和已保存资料分册，分册有原文依据；历史分册会明确标注，不能当成最新客户结论。
6. **保持状态约束**：同订单发出去了、已发车、已出境应作为已走货事实；登记出库滞后不等于未发货。已走货／履约批次不产生催备货噪声；独立新需求可以新建批次与行动。人工完成、暂停、纠正和角色确认有版本控制。
7. **schema v11**：增加分册和进度表，升级前自动生成 `pre-v11-*.sqlite3`，已有消息、用量、名单和人工处理保留。未加入业务经验学习、经验编辑页或自动记忆注入。

## 使用

按 [部署与接入SOP](DEPLOYMENT_SOP.md) 更新并启动 `start --pilot`。选择一位联系人分析；进度显示暂停时，预算允许后再次点击同一联系人继续。升级后原客户需重新分析，以完成整段历史的分册整理；无需重新导入微信消息。

## 验证与限制

- 已通过合成业务回归：较早发货记录被后续500多条消息淹没仍会送入资料整理；多次暂停续跑覆盖所有来源；日期数值差异不删除已发车批次；已走货后独立新需求仍产生行动；白名单、授权和版本隔离生效。
- 自动化测试使用模拟模型，验证读取、归集、持久化、预算及状态链路；没有用户本机完整聊天或真实DeepSeek业务评测，不能声称准确率已达标。必须继续核对真实客户结果。
- “全部”仅指本地已归档且已授权的相关会话。源端未同步、隐藏、删除的历史不保证覆盖；媒体仍未OCR。未识别媒体／有疑点时，新行动需关键确认，不能据此说没有需求。
- 分册整理会压缩措辞，不能保证模型不漏事实；原始消息与各级分册可查，最终总结不替代原文。每级最多80条事实；大汇编逐级归纳，最多8级。不能有效收敛、单条源消息超60000 JSON字符、最终请求体过大等会明确报错，保留已完成分册。
- 分册复用依赖消息ID／修订／模型及内容，最终发布还会校验来源范围与文档版本。源变化时不能覆盖旧版本；续跑可复用未改变分册，可能需重做变化处。
- 新引擎尚无自动日次调度、完整语义批次去重、OCR、历史激活或话术推荐。不带 `--pilot` 仍使用旧模型后台。
